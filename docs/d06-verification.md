# D06 澄清后继续原 Feed：交付验证

## 1. 用户结果与硬约束

R1：原 Feed 因信息不足进入问答，含糊回答继续等待；明确回答足够后自动继续原请求，无须重发。
R2：本轮原话只解释、提交一次；筛选保留原请求范围并使用同一份已提交的有效事实。
R3：普通更新、反馈、错误或重复 token 不启动其他等待请求；同一关联最多执行一次筛选。
R4：准备失败保留有效关联，执行后的链接、业务空、来源/判断未完成和存储错误保持各自含义，不自动重放。

五个 MCP 工具、公开输入和封闭结果类别稳定。问答限当前进程，个人事实持久化；没有新增通道依赖、持久请求、恢复机制或真实服务操作。

## 2. 被降为候选的设计与流程

删除第二套等待请求表、重复请求快照、持久恢复、后台重试及额外充分性模型调用。沿用 D05 的 `clarification.originalText` 保存原意图；`currentText` 仍是当前回答。首次请求和续答共同使用 D04 的筛选代码，不再次调用 `request(originalText)`。

## 3. 最小方案与更小反事实

只在现有 PendingEntry 增加可选 `resumeFeed`。带标记续答启用既有 `assessForFeed`；模型按原 Feed 范围判断更新后事实，应用沿用已有有效事实过滤及结构下限。

提交事实时同时检查 generation 与 token 身份；写成功后，不足则随剩余问题转移标记，足够则消费标记并捕获原意图和有效快照。随后进入现有请求队列的共享 `runPreparedFeed`，执行时确定观察时间。其他剩余问题可以留下，但不携带已执行 Feed 的标记。

不加标记无法区分普通问答与等待中的 Feed；扫描所有问题会误触发其他请求；重新调用原请求会重复解释和提交；在筛选结束后才消费会容许重放。单个进程内标记满足本次结果，不需要另设调度责任。
