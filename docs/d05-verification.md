# D05 澄清问题并应用回答：交付验证

## 1. 用户结果与硬约束

R1：缺信息、含义或范围不明、负面反馈原因不明时追问；明确时不重复问。
R2：只修改明确涉及的事实，明确部分立即提交，剩余部分继续澄清。
R3：多轮保留最初表达、显式引用、当前问题和剩余范围；成功一轮消费旧 token，失败保留有效关联。
R4：独立更新与反馈不启动推荐，复用 D04 的内部有效事实与请求范围足够性结果。

五个 MCP 工具和既有封闭结果类别保持稳定，通道无关，敏感内容不进日志。个人事实持久保存，问答限当前应用进程。D06 的恢复原 Feed 不在本次实现内。用户已于 2026-09-06 最终授权合入本地 main 并更新任务文档；推送、部署、真实账号与模型验收未获本次授权。

## 2. 被降为候选的设计与流程

删除持久问答恢复、完整对话历史、跨文件事务、后台重试和第二套足够性判断。旧 `pending-feedback.json` 不读取、不迁移、不删除；没有新增服务、调度器或公开结果字段。

中途才明确的原对象可通过两入口共有的 `resolvedReferenceText` 填入尚缺失的问答引用，已有显式引用保持原值；它属于 C3，不是新的问答历史或持久字段。

模型续答必须给出 `remaining: { question, unresolvedScope }` 或 `remaining: null`。首次明确的普通更新仍可省略 remaining，避免扩大 D02/D04 的无澄清协议。反馈与个人信息入口都能携带 D02 ContextChanges；校验完整目标后才整批提交。

## 3. 全局最小方案与更小反事实

扩展现有两个解释入口；当前事实与问答原始对象一并交给模型。单个进程内 Map 关联问答；提交复用 contextQueue，同时核对事实 generation 和该 token 对应的关联身份。事实先写，必要反馈记录随后写，全部成功后才消费/轮换 token。模型失败返回带原问题的 incomplete；存储失败仍按原契约作为错误，但有效关联不消费，重试读取当前事实。已写事件沿用 token 派生 ID 去重，内容不同的同 ID 事件作为存储故障拒绝。

什么都不新增会保留已复现的引用丢失和旧 token 残留；一次性验证不能让运行时多轮回答保留对象；要求用户每轮重述不满足 R3；只提问不提交独立明确部分不满足 R2。已确认事实留在事实存储，不再复制进问答历史。

## 5. 0→4 增加阶梯、逐个删除与机械校验

S0→C1：原代码无法对个人信息产生问题，原因不明的负面反馈可直接 completed。
C1→C2：只有问题仍无法提交混合表达中的明确部分。
C2→C3：提问和局部提交仍无法保留后续回答的原对象，旧实现已经复现引用被上轮回答替代和 token 残留。
C3→C4：内部准备需要同一份提交后事实和范围判断，不能另起足够性解释器；该责任由 D04 先行提供。

逐个删除 C1/C2/C3/C4，分别恢复假完成、明确部分被阻塞、原对象丢失、内部准备缺失的对应失败。原执行者预算与低预算挑战均计四项，并通过 `validate_complexity_budget.py`；实施没有新增第五项长期概念。预算 JSON 只作临时审计材料，不进入运行时。
