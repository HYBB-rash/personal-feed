## 建议先决定什么

关键是：**补充信息时，要继续在普通聊天里回答，还是可以在专门的回答框里填写？**

两者都可以朝“固定程序负责交接”发展，但代价不同。我倾向于：如果回答框可以接受，先验证服务直接收回答案这条路；如果普通聊天不可让步，就验证 Codex 专用接入程序。先选一个做小范围验证，不同时建设两套。

这不是已有可靠成品之间的选择。下面两条都有协议或接口依据，**本机完整交互尚未验证**；验证失败需要回来调整方案。

## 三个修复方向如何落地

| 方向 | 具体要求 | 用户能察觉的变化 |
| --- | --- | --- |
| 减少 Agent 承担的机械责任 | 固定程序保存问题关联、更新关联、把答案交给原请求；服务保证原 Feed 只续做一次。 | 回答后自然继续，不需要重发请求或提醒它带参数。 |
| 错误用法可见 | 结果区分“信息保存了”和“原 Feed 继续了”；接入程序发现预期续答却未续答时，明确报告断点。 | 不再用一句“已记录”掩盖原请求没有推进。 |
| 中断有去向 | 有效问题继续等待；处理失败保留有效问题；无法关联时明确结束旧请求，说明哪些信息确已保存、下一步能做什么。 | 知道是在等回答、已经完成，还是需要重新请求。 |

**能力限制：**服务单独收到不带关联的普通更新时，无法判断它是否来自另一个任务的续答。不能靠“发现系统里有旧请求”就报警或自动续做；可靠检测必须放在知道当前交互归属的接入程序里，或者让答案直接回到原调用。

## 路线一：保留普通聊天，固定接入程序负责交接

使用体验保持“请求 Feed → 系统追问 → 在聊天里回答 → 继续”。接入程序在工具结果被 Agent 裁剪前取到完整关联；下一次对应工具调用时自动带回。Agent 仍判断当前话语适合哪个业务工具，服务仍解释用户意思；关联的保存与传递不再依赖临时生成的调用代码。

可验证的入口是 Codex 的工具调用前后钩子：官方说明允许改写输入，也覆盖代码模式内的工具调用。但官方同时说明它不是完整强制边界，部分失败会继续执行，子代理还共享父任务标识。因此只能作为候选，不能直接宣称“加钩子就保证可靠”。[Codex Hooks 官方文档](https://learn.chatgpt.com/docs/hooks)

最小验证必须回答这些问题：

- 本机普通工具调用和代码模式调用是否都会经过接入程序，完整结果是否能在文字裁剪前保存。
- 接入程序出错、未启用或状态写入失败时，能否明确暴露问题，避免继续表现成成功。
- 两个任务、个人信息问答与反馈问答、并发调用能否分开；无法确定归属时应停止续答，不能猜一个关联。
- 新问题替换旧关联、一次 Feed 结束、无关收藏调用、取消与中断，是否各自正确处理状态。

**代价与边界：**新增需要安装和维护的 Codex 接入部分。它应独立于通道无关的服务核心；不能把 Codex 任务编号塞进业务接口。若跨钩子进程需要短期私有状态，应明确修改现有“调用方不写 token 文件”的接入约定，并限定生命周期，不能顺便扩展成跨任务恢复。现有运行时和包代码禁止宿主标识，因此专用接入部分的独立边界也需先确认。

如果这些验证表明钩子无法稳定承担责任，就不能把更长的 Skill 当作兜底保证；届时再讨论更强的接入方式，当前不建设新平台。

## 路线二：服务直接请求回答，在原调用里继续

使用体验变成“请求 Feed → 出现一个补充信息的回答框 → 填写并提交 → 继续”。问题仍可用自然语言，答案可以是自由文本；改变的是提交答案的位置。

MCP 的 elicitation 支持服务请求用户输入，并收到提交、拒绝或取消结果。方案是在同一次 Feed 调用里等待答案，再由服务继续处理，省掉 Agent 跨轮保管和传回关联这一步。[MCP Elicitation 规范](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation)

Codex app-server 文档已有对应表单请求，本机 CLI 0.153.4 生成的接口定义也包含该消息。这支持继续验证，但不能证明当前桌面、权限模式和本项目 HTTP 服务已经能完成整个交互。[Codex App Server 官方文档](https://learn.chatgpt.com/docs/app-server#mcp-server-elicitation-requests)

最小验证必须覆盖：

- 本机桌面是否展示自由文本问题，提交、取消是否回到正确的原调用。
- 连续两次追问、等待较久、主动中断和服务关闭时，是否有明确结果，是否保留已提交的信息。
- 普通聊天中途插话是否中断回答框；用户在聊天里补充而没有提交表单时，系统如何说明当前状态。
- 客户端不支持此能力时，明确说明限制；不得悄悄降回已知不可靠的跨轮交接后仍宣称同等保证。

**代价与边界：**改变补充信息的入口，也需要改服务的连接管理。当前 HTTP 实现每个 POST 都创建并关闭 MCP 实例，初始化时的客户端能力不会保留到下次请求，不能仅加一行“弹框”就完成。应先用临时服务验证能力协商与回答回送；若采用 MCP 协议会话，必须同步澄清现有无状态及 session identifiers 禁止条款的范围，核心不接收宿主任务标识。

等待用户输入的时间还要与现有调用超时分开核对，不能直接沿用当前业务处理时限。此路线最初只应用于阻塞 Feed 的必答问题；其他不阻塞推荐的澄清仍保留原有语义，避免为了问答而扣住已经可交付的 Feed。

## 两条路线都应包含的基础修复

1. **工具交接数据完整。** 修正本次“只提取文字就丢关联”的返回缺口。MCP 规范建议结构化结果同时提供 JSON 文本镜像；它能修本次裁剪路径，但单独做仍依赖 Agent 正确带回关联。[MCP Structured Content](https://modelcontextprotocol.io/specification/2025-06-18/server/tools#structured-content)
2. **结果表达准确。** 信息更新结果只说明实际保存情况；有实际 Feed 结果才说推荐已继续。模型处理失败、内容源失败和业务空分别使用既有类别及原因，不把正常业务空改成 MCP 错误。
3. **安全诊断足够。** 只记阶段、是否收到/接受关联、是否存在待续 Feed、是否实际续做及固定失败原因；不记录用户原话、内容原文、URL 或 token。
4. **中断处理保持适度。** 沿用原有约定：不保证跨任务或服务重启恢复旧请求，已保存个人信息继续保留。关联失效时明确告知可重新请求；仍有效时直接续做，不要求用户重发，也不暗中重放旧请求。

第 1 项需要同步整理文档用词：当前“token 不进入可读文本”若包括工具的机器交接文本，就与 JSON 镜像冲突。可将边界明确为“不出现在用户回复和诊断日志”，机器交接载荷允许包含；这是拟议调整，尚未改动现有合同。

## 实施与验收顺序

1. 先选交互路线，验证最小接入能力；使用临时目录、假模型与内容源，不改现有验收服务。桌面交互验证另行明确执行范围。
2. 先加能够复现丢关联的失败测试，再实现所选路线和共用修复；同步更新 D00、MCP 与 Skill 中受影响的边界。
3. 检查“有效续答”和“无原请求的普通更新”这对相同输入；前者只续做一次，后者不推荐。再检查重复提交、并发、两种问答并存、旧关联、取消和失败。
4. 最后用普通新任务做多轮验收，不预先教 Agent 如何保管 token。必须走过真实的“含糊回答 → 追问 → 补足 → 实际 Feed 结果”，并另验中断后的明确说明。

服务测试、接入测试、真实模型判断和用户对推荐质量的验收分别记录。不能再以“手动把参数传对的测试通过”代替“正常聊天可靠”。五个 MCP 工具名及闭合结果类别保持不变。

## 当前讨论只需要先定一个点

**补充信息时，专门的回答框是否可以接受？** 如果可以，我建议先验证路线二；如果普通聊天是必须保留的体验，就先验证路线一。断开旧请求后允许重新请求、保留已存信息等已有边界继续沿用，不扩大为恢复平台。
