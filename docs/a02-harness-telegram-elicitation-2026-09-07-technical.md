# Personal Feed 修复方案：技术依据与详细草案

本附件保留调查证据、技术限制和实现候选。讨论方案请先读[简明版](/home/herman/Projects/personal-feed/docs/a02-harness-telegram-elicitation-2026-09-07.md)；附件中的接口和实现方法仍需验证，不代表已经落地。

2026-09-07。只读调研与方案修订，未修改程序、接入配置或运行服务，未发送 Telegram 消息。

## 结论

**路线二应按通用服务能力设计，以 DeepSeek Harness + Telegram 为首个实际接入目标。** Codex 只是此前暴露问题的调用端，不能成为 Personal Feed 的产品依赖。用户已认可表单与普通聊天可以共存，无需再询问是否接受表单。

**用户进一步明确：这是监控型信息流，必须区分后台监控与主动交流。** cron 自动调用时用户未必在场，不应反过来追问需求或等待回答；用户看到内容后主动聊天、交底时，才可以通过表单等待补充或确认，再更新认识。下文据此修订，不再把后台晚答恢复当作默认需求。

**需要 telegram-gateway 更深的支持，但目前没有证据要求另做一款 Telegram 客户端。** 可以在现有 Telegram 内先实现“问题消息、选项按钮、指定回复、明确提交/取消”，再按体验需要增加 Mini App 内嵌表单。主要工程量首先来自可靠的请求归属、等待、收答与续做，而不是画一个表单。

前一稿把“路线二”同时等同于专门回答框、一次长工具调用，是不充分的。现在拆开三个问题：

| 要决定或实现的事 | 当前判断 |
| --- | --- |
| 谁负责把答案交回原请求 | 固定程序负责，模型不保管关联、不代填答案。 |
| Telegram 怎么呈现 | 原生消息与按钮足以验证基本体验；复杂的多字段编辑可以再用 Mini App。 |
| 哪些调用允许提问 | 后台监控禁止提问和等待；用户主动交流时允许必要的表单问答。 |

### 已明确的两种使用模式

| 模式 | 输入与行为 | 交互边界 |
| --- | --- | --- |
| 后台监控 | cron 按已有关注和认识，检查现在是否有值得提供的内容。 | 不向用户追问、不创建等待用户的监控任务；有实际可交付结果才走内容投递。 |
| 主动交流 | 用户看完内容后聊天、交底，表达兴趣与已有认识；需要澄清或确认时可以呈现表单。 | 人在场时允许等待回复或提交，答案由固定程序交回业务服务并更新认识；取消或中断按既有边界处理。 |

两条路径共享已保存的个人信息：主动交流更新认识后，后续监控使用更新后的信息。普通交底不等于发起一轮新推荐；只有存在当前有效的推荐请求时，补足信息才续做该请求。

**方案推论：**后台已有信息足以判断时照常筛选；若不足以作出有依据的价值判断，就结束本轮并保留准确的内部原因，不编造用户认识，也不把补充资料变成一次 Telegram 提问。信息不足与“查过但没有合适内容”仍需在内部区分。

调用是否允许人机交互，应由宿主的固定接入代码依据执行入口确定，并以通用策略交给服务；不能让 Agent 临时猜测用户是否在线，也不能让 Feed 根据 cron、Telegram 或聊天编号分支。客户端支持表单只是能力条件，不代表该客户端发起的每个请求都允许提问；后台应在进入追问流程前禁用交互，不以自动拒绝已弹出的表单充当实现。

## 关键证据

### 1. MCP 支持服务提问，但不规定必须弹网页表单

MCP `elicitation/create` 由服务经客户端向用户请求输入。`form` 描述的是结构化输入，具体界面由客户端决定，因此翻译成 Telegram 内的按钮和回复也是可行方向。客户端必须声明支持能力；不能把“不支持交互的 Agent”视为同样可以完成问答。规范要求清楚标明提问服务，允许审阅、修改、拒绝与取消。[MCP 2025-11-25 Elicitation](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation)

**主动交流中的拟议流程：**业务服务提出必要问题 → Harness 接入程序呈现问题 → Telegram 收到人的明确回答 → 固定程序校验并回给原 MCP 调用 → 服务更新个人信息，并在确有待续推荐时继续。自由文本保持原话，不让外部 Agent 归纳后再冒充用户提交。后台监控不进入这条流程。

### 2. Harness 已有问答服务，MCP 桥接仍缺一段

本轮核对的本地官方安装是 **`@deepseek-ai/dsh` / `dsh-mcp-client` 0.1.2-rc.1**，不是未来 VM 的运行验收，也没有据此断言所有后续版本都一样。

- `ctx.userQuestions.ask()` 已提供“提问并等待回答”的公共能力，可注册按 Agent 区分的回答提供方，支持选项和自定义文字。[已安装公共接口](/home/herman/.dsh/runtime/node_modules/@deepseek-ai/dsh-user-questions/lib/types/index.d.ts)
- 该版本 MCP 客户端以 `capabilities: {}` 建立连接，没有声明 elicitation，也未注册相应请求处理器；公开配置没有添加这类处理器的入口。**仅在 Feed 服务端增加 elicitation 不能贯通。**[MCP 客户端实现](/home/herman/.dsh/runtime/node_modules/@deepseek-ai/dsh-mcp-client/lib/index.js:612)、[公开配置](/home/herman/.dsh/runtime/node_modules/@deepseek-ai/dsh-mcp-client/lib/types/index.d.ts)
- 问答服务拒绝直接从仍受其他 Agent 管理的子代理发起人机问答；主动交流中的委托任务要有明确的宿主交互负责人，不能省略身份绕过这条限制。后台监控按本次确认的需求不使用问答能力。[问答校验](/home/herman/.dsh/runtime/node_modules/@deepseek-ai/dsh-user-questions/lib/index.js:52)
- 原 MCP 桥虽然保留结构化返回值，普通模型文本呈现仍提取 `content` 中的文字。这说明本次交接缺口并非只与 Codex 有关，迁移宿主不等于自动修复。[结果呈现](/home/herman/.dsh/runtime/node_modules/@deepseek-ai/dsh-mcp-client/lib/index.js:218)

按照 dsh-plugins 当前规则，方案不修改或补丁化上游。可研究一个独立的 Harness 接入插件，使用公共工具注册与问答接口，自己持有支持 elicitation 的 MCP 连接，替换所选服务器的现有接入。它与 Personal Feed 分包、分职责，不能把 Harness 依赖带入 Feed 服务。**这比“给现有客户端加个配置”工作量大，仍需隔离原型证明。**

### 3. telegram-gateway 的主要缺口是等待时仍能收答

核对范围是本地 dsh-plugins 源码 `cc18ab8`，未核对远端当前发布物。

当前 gateway 在轮询中等 `dispatchInbound()` 和 Agent 完成本轮，才处理后续更新。如果本轮工具一直等待 Telegram 答案，轮询自身又被本轮挡住，就无法及时取回答案；即使表单已经发出去，这条原生收答路径仍会卡住。这是根据控制流得到的结论，尚未做运行重现。[收取和派发](/home/herman/Projects/dsh-plugins/telegram-gateway/src/index.ts:532)、[等待 Agent 完成](/home/herman/Projects/dsh-plugins/telegram-gateway/src/index.ts:260)

当前收件类型只处理 `message`，发送选项只有回复消息编号；没有按钮回调、表单提交或 `user-questions/request` 的回答提供方。已有引用回复目前被整理为模型参考文本，不能当作已完成程序级关联。[Telegram 类型与发送接口](/home/herman/Projects/dsh-plugins/telegram-gateway/src/telegram-contract.ts:135)

拟补能力：

| 能力 | 必须解决的具体问题 |
| --- | --- |
| 收件与任务执行分开 | 同一个轮询器持续收消息；答案和取消直接送往等待者，普通消息按既定顺序处理。不能另开第二个 poller。 |
| 通用问答提供方 | 接住 Harness 的问题，在指定 Telegram 对话呈现；提交后直接返回答案，不再经过一次模型转述。 |
| 明确请求归属 | 问题消息、按钮和提交对应一个有效交互；核对允许的用户、对话和调用来源，避免串到 Web、cron 或另一个任务。 |
| 生命周期 | 等待、提交中、完成、取消、失效要可见；重复点击不重复执行；过期回复不能接到新问题上。 |
| 单一发送责任 | 提问与最终 Feed 各有明确发送者；不让 gateway、Agent 总结和后台投递重复发送。 |

这些是通用的人机问答能力，不应把 Personal Feed 的兴趣、认识、筛选规则写进 gateway。

### 4. Telegram 原生交互和 Mini App 是两档工作量

**原生交互候选：**问题消息可用 `ForceReply` 打开对指定消息的回复输入，用 inline keyboard 收选择、提交或取消动作；按钮回调需要及时确认。可据此做一个问题一组交互，输入后允许核对再提交。它不是自动生成的多字段网页表单，具体易用程度仍需手机实测。[ForceReply](https://core.telegram.org/bots/api#forcereply)、[InlineKeyboardButton](https://core.telegram.org/bots/api#inlinekeyboardbutton)、[CallbackQuery](https://core.telegram.org/bots/api#callbackquery)

**Mini App 候选：**可以直接在 Telegram 内提供网页表单，适合同时编辑多个字段、查看原值和统一提交，无需另装 Telegram 客户端。它新增前端页面、可访问的网页入口、身份验证、问题读取与提交接口、移动端适配；不同启动入口的回传方式也不同，不能假定所有入口都能使用 `sendData()`。服务端须验证 Telegram 提供的初始化数据，不能信任浏览器自报身份。[Telegram Mini Apps](https://core.telegram.org/bots/webapps)

**建议：**先证明同一个通用问答能力能由 Telegram 原生界面完成，再判断是否增加 Mini App。两种呈现使用相同交互归属与提交规则，避免升级界面时重写 Feed 业务。

### 5. 自动提供 Feed 与问答属于两条相连的责任链

自动提供内容仍由宿主侧触发并投递：**调度/任务负责人 → 调用独立 Feed → 取得实际结果 → Telegram 投递**。Feed 不因此增加 Telegram 凭据、聊天标识或自己的调度器。

已有 dsh-cron 会调用 gateway 提供的 `dshTextDeliveryV1` 投递文本，返回 delivered / failed / uncertain；这是可复用的接口证据，不是新 Feed 已经接入或真实推送通过。[cron 投递边界](/home/herman/Projects/dsh-plugins/dsh-cron/src/scheduler.ts:351)、[gateway 提供方](/home/herman/Projects/dsh-plugins/telegram-gateway/src/text-delivery.ts:45)

自动请求缺少个人信息时，不向用户发问题、不等以后回答来完成这一次监控。主动交流中的认识更新由后续监控使用；不把已经结束的旧监控任务重新挂回聊天。支持 elicitation 只解决允许交互时的提问收答，不自动提供定时推送或任务恢复。

## 建议修复顺序

### 第一段：验证最短的路线二

先用同一组缺少个人信息的输入，验证后台与主动交流两种调用策略：后台不得调用问答提供方或等待用户，主动交流才允许提出必要问题。

主动交流的隔离原型使用假 Feed 和假 Telegram 收发：一个问题、一个自由文本答案、一个实际更新结果。接入程序必须持有明确的原调用，不能使用“最近一次请求”猜归属。验收时不让模型代管问题 token。

并行存在多个 MCP 调用时，要证明服务器发来的问题能定位到精确调用与交互负责人；不能只根据服务器名或全局“当前 Agent”分配。原型可用每个活动调用独立的 MCP 连接缩小归属问题，再测连接开销与生命周期，而不是一开始造共享连接恢复平台。

再完成四个客观检查：等待时仍能收答、答案直达原调用、取消可以结束等待、旧/重复提交不会续错或重做。使用 Harness 公共能力，不修改官方包，不连接真实模型与 Telegram。

### 第二段：接入真实 Personal Feed

服务增加协商后的 elicitation 支持，并遵守每次调用的交互策略，沿用现有个人信息更新、问题判断和 Feed 结果逻辑。允许交互时才进入单次调用内问答；后台调用不会因客户端具备表单能力而等待人。当前 HTTP 每个 POST 新建 MCP 实例，需改接入生命周期，保留客户端能力并支持服务器请求及答案回送；不能仅改结果文字。[当前服务接入](/home/herman/Projects/personal-feed/src/service/server.ts:100)

五个工具名称和闭合业务结果类别保持稳定。取消、不支持交互或没有可用回答方，要准确返回现有未完成/需输入语义；不能等到超时才伪装业务空。普通调用方仍可使用服务，但未提供人机交互能力时，不能承诺自动完成问答。

原有问题/token 交接可作为明确标注能力边界的兼容方式。若先用固定桥接代码把现有问题/token 结果转为 Harness 问答来验证 Telegram 体验，应明确它只是过渡原型，不能冒称原生 MCP elicitation 已完成。

### 第三段：真实 Telegram 和主动 Feed 验收

在明确授权的测试 bot/环境验证主动交流中的提问、修改、提交、取消和失效后回复；再接宿主自动触发与唯一投递。后台缺资料时也必须验证没有表单、没有等待，没有把问题当作推荐内容推送。最后验证主动交流更新的认识会被下一轮监控使用，且不会复活旧监控请求。已有明确资料时直接处理，不为了表单强行打断每次交流。

若原生交互在多字段编辑、长答案或多问题切换上明显不好用，再做 Mini App。原生问答可评为中等规模改动，完整 Mini App 会增加界面与接入工作量；后台晚答恢复不在本轮范围。这是根据模块责任作出的相对估计，未做原型前不报确定工期。

## 反证或限制

- **支持通用 MCP 不等于支持所有 Agent 的完整交互。** 原始服务可以通用；可靠人机问答需要调用宿主提供相应能力，无法由服务单方面保证。
- **有 `ask_user_question` 不等于 MCP 问题已经接入。** 若仍让模型读问题、再自行调问答、再自行带 token 返回，关键机械责任没有消除。
- **表单不等于跨中断恢复。** 一次 MCP 请求仍受服务、客户端、Agent 取消与网络生命周期约束；等待时间和业务计算超时需分别设计。
- **收件不阻塞不等于同一个 Agent 能并行聊天。** 要让等待 Feed 时仍处理其他聊天，需由宿主明确安排等待任务与交互根的职责，不能简单把所有新消息并发塞给同一个 Agent。
- **Mini App 不要求暴露 Feed 本身。** 可由网关/交互层承接网页请求，再从受控宿主连接 Feed；Feed 继续通道无关。若 Harness 与 Feed 不在同一 VM，loopback 如何连接是额外部署边界，尚未核实，不自动扩成公网服务。
- 本轮没有运行原型、做 Telegram 手验或检查 VM 上的当前版本。读取本地源码和官方资料不能替代这些验证。

## 已收敛的需求与实施边界

用户已通过区分场景回答了前一稿的“隔几个小时续答”问题：**后台不问，主动交流才等人。** 不再要求用户为后台监控选择长时间问答或跨重启恢复方案。

主动交流沿用当前持续使用中的问答边界，不因本次修订新增跨中断或服务重启恢复；已提交的个人信息保持原有持久保存要求。具体交互策略字段、问题超时和 Telegram 原生呈现属于待设计与验证的实现细节，尚未修改 D00 或公开接口。

本稿是后续修复依据，不代表代码已经实现、后台监控已经接入或 Telegram 问答已经可用。
