## 2. 个人信息与局部修改

### 2.1 事实与足够信息

复用现有 `PersonalContextFact`：长期关注使用 `long_term_interest` 及 `include/exclude`；已有认识使用 `existing_knowledge` 及 `asserted/uncertain`。不新增“新手”事实类别。

- 维护状态可以保留 `uncertain`；交给候选判断的有效信息必须排除这些认识。待澄清部分不能用来认定某篇内容“用户已经知道”。
- 明确的新手陈述使用 `existing_knowledge/asserted`，例如“我在家庭照护领域刚入门，没有相关基础”。它是用户明确提供的知识边界，不等于已有认识没有提供，也不能扩大为用户在其他领域都没有知识。
- 个人信息维护向请求协调交出 `facts`（本次确定的有效事实）、`sufficient`（是否足够支持原请求的关注匹配和信息增量判断），以及尚需澄清的问题。`sufficient` 不能仅由事实条数或“存在一条认识”得出；只有其他领域的认识也不能自动补足本次缺口。
- 只有明确、相关的长期关注和知识边界都足够，才能开始原 Feed。已有认识可以是明确的新手状态。待澄清部分排除后仍足够，则可以继续；不要求先解决所有疑问。
- 普通明确更新不要求凑齐整份画像；没有 Feed 时，只因另一类信息尚未提供，不额外发起画像补全流程。表达本身含义或范围不明时仍可澄清。

价值判断使用同一次准备交出的有效事实；不会每条候选重新推测画像。只收到、点击或收藏内容不构成已有认识；负面反馈没有明确个人信息含义时，也不产生画像变更。

### 2.2 局部变更的共同表达

以下是个人信息解释与提交之间的语义形状，不是新公开 MCP 工具，也不要求新模块或新存储：

```ts
type ContextChanges = {
  additions: readonly PersonalContextFact[]
  replacements: readonly {
    target: PersonalContextFact
    replacement: readonly PersonalContextFact[]
  }[]
}
```

| 意图 | 表达及提交后结果 |
| --- | --- |
| 新增 | 放入 `additions`，无旧事实被隐式删除 |
| 保留 | 不提交针对该事实的替换，原事实保持不变 |
| 撤回 | `target` 指向本次读取的原事实，`replacement: []` |
| 更新／缩小范围 | 替换明确涉及的 `target`；替换列表可以保留明确部分，并把仍有疑问的部分表达为 `uncertain` |

`target` 是解释时实际读到的完整原事实值，匹配类别、陈述及其确定性或取向，不依赖永久编号或模型猜出的原文。一个目标在一次变更中只出现一次；不在 `replacements` 中的事实一律保留。若无法可靠定位目标，先澄清，不选择一条“看起来像”的事实修改，也不撤回整个主题或整份画像。

明确部分可以先提交，其他部分继续待澄清；前提是明确部分的对象和范围自身已经清楚。提交时目标已经变化，则沿用已有冲突结果，重新读取再处理，不强行覆盖。无需为此另建版本平台。

后续 `observe_context.appliedCount` 表示本次实际提交的变更项数：新增一条计一项，替换或撤回一个目标计一项；相同事实的重复新增、等值替换不计入。它不是画像事实总数，也不表示信息已经足够。下游验证以实际事实变化为主要依据。

## 3. 问题、回答与原请求的关联

### 3.1 需要保留的含义

一次有效续答关联至少能够找回：当前问题、它针对的个人信息或反馈、尚未解决的部分，以及是否存在仍在等待的原 Feed。原 Feed 存在时还保留其最初用户表达中的请求意图和限制；后来一句普通补充不能把它改成无范围的新请求。

这些含义可以由应用内当前等待状态承载，不规定新增持久字段或存储格式。沿用不透明 `continuationToken` 的关联方式；核心不接受聊天、消息或会话编号。

- 对应问题的回答只调整已明确的部分，已解决部分从待问范围移除。仍不明确时，保留其疑问，不重复询问已答清的部分。
- 普通交流可以新增相关确定信息，不要求它逐字回答旧问题。它足以支持原 Feed 时也要继续；旧疑问未被回答的，仍保持待澄清，不能凭新增信息假装它已解决。
- 原 Feed 开始续做后，交出这次实际结果，并移除该等待关联中的 Feed 意图；即使另有问题仍需澄清，后来回答也不能再次触发这次已结束的 Feed。
- 原请求若以来源或判断失败结束，仍如实交出未完成；不因此留下一个由后续交流自动重试的后台任务。
- 中断可以终止这次未完成的工作，不保证找回或重放。已有个人信息保存要求不受此影响，也不要求主动破坏能够自然延续的问答。

### 3.2 调用方的责任

调用方只在当前有效的问答中保留和传回 token，不向用户展示，不自行改写，也不建立跨会话恢复设施。

对用户明确的 Feed 请求调用 `request`；普通个人信息表达或个人信息澄清回答调用 `observe_context`；语义反馈及其回答调用 `process_feedback`。有当前关联时，调用方自动携带 token；用户无需声明“这句话是回答”。服务依据关联中的问题对象和本次原话解释输入，不能只因出现 token 就把所有新表达强行认作旧问题的答案。

`currentText` 始终是本次用户消息原文。继续原 Feed 使用已保存的原意图与本次更新后的信息；不要求调用方重发旧消息，也不把旧原文冒充新的 `currentText`。一次本轮表达只完成一次个人信息观察与提交；内部续做不再把刚提交的回答重复作为新观察执行。

## 4. 五个工具的字段合同

### 4.1 保留所有现有结果类别

下表的顶层 `status` 与 `stage` 与基线一致；可选字段见下一小节。

| 工具 | 顶层 `status` | `incomplete.stage` |
| --- | --- | --- |
| `request` | `one_link`、`business_empty`、`incomplete` | `context_observation`、`personal_context`、`source_window`、`judgement_execution`、`conflict`、`shutdown` |
| `observe_context` | `applied`、`ignored`、`already_observed`、`incomplete` | `context_observation`、`conflict` |
| `process_feedback` | `pass`、`completed`、`discarded`、`needs_input`、`incomplete` | `feedback_interpretation`、`feedback_commit`、`conflict` |
| `record_feedback` | `saved`、`unsaved`、`already_saved`、`already_unsaved` | 无 |
| `list_saved` | `completed` | 无 |

业务空、等待澄清和未完成都是正常结果。身份验证、非法输入和存储故障遵守既有 MCP 错误边界；不能把错误转成业务空。正文、用户原话、完整链接、token 或凭证不能写入日志。

### 4.2 必要字段增量

| 位置 | 待实现增量 | 确切含义 |
| --- | --- | --- |
| `request` 输入 | 无 | 仍为 `{currentText}` |
| `observe_context` 输入 | 可选 `continuationToken` | 本次原话与当前有效问题及原 Feed 的关联；不是新 Feed 请求 |
| `process_feedback` 输入 | 无新增字段 | 仍为 `{currentText, referenceText?, continuationToken?}` |
| 上述三个工具的业务结果 | 可选 `question`、`continuationToken` 对 | 当前剩余问题与其有效关联；两者同时出现或同时省略。原 `process_feedback.needs_input` 仍要求这两个字段 |
| `observe_context`、`process_feedback` 的业务结果 | 可选 `feed` | 本次信息更新之后实际继续原 Feed 所得的既有 Feed 结果；未尝试续做时不出现 |
| `record_feedback`、`list_saved` | 无 | 不承担个人信息问答或 Feed 续做 |

token 仍使用既有的 32 字节随机值及 43 字符 base64url 表达，不赋予用户身份或通道身份含义。格式非法按既有非法输入处理；格式合法但关联已中断、无法使用时，不猜测旧问题或原 Feed：`observe_context` 返回 `incomplete/context_observation`，`process_feedback` 返回 `incomplete/feedback_interpretation`。无需增加失效恢复协议。

`feed` 复用基线 `RequestResult` 的 `{status, url? , stage?}`：只有一条链接、业务空、未完成三类；不另造 `resumed` 等状态。嵌套 `feed` 不再携带问题或下一层 `feed`，尚有问题统一放外层 `question/continuationToken`，避免同一个回答有两套关联。

| 实际情况 | 结果组合与调用方呈现 |
| --- | --- |
| 原 Feed 因个人信息不足等待 | `request` 返回 `incomplete/personal_context` 和问题/token；说明仍在等信息，不呈现成空或已结束 |
| 普通明确更新，无 Feed、无疑问 | `observe_context` 返回 `applied`；没有问题，也没有 `feed` |
| 提交了明确部分，尚有问题且仍不足 | `observe_context` 返回 `applied` 和剩余问题/token；未续做，所以没有 `feed` |
| 含糊回答没有产生明确变化 | `observe_context` 返回 `ignored` 和当前剩余问题/token；问答仍有效，不能因 `ignored` 结束它 |
| 更新补足了信息 | 返回更新结果及 `feed`；调用方呈现真正的 Feed 结果，不能只说“已记住” |
| 还有疑问，但剩余确定信息足够 | 允许问题/token 与 Feed 结果同时出现；`request` 直接携带自身结果，更新工具在 `feed` 中携带结果。疑问继续，已结束的 Feed 不再等待 |
| 来源或判断未完成 | 如实呈现相应 `incomplete`；更新已经提交与 Feed 未完成可以同时成立 |

新增字段需要后续任务同步应用类型、MCP 严格 schema 和接入说明。当前严格 schema 尚不接受这些增量，不能把本文件的示例直接发送给当前服务并声称应该成功。

## 5. 四类完整交接示例

下列前置事实、用户话语、链接和返回值均为受控示例，不是真实用户资料、真实 X 观察或运行记录。重复字母组成的 43 字符 token 仅用于说明关联，实际服务仍随机生成。字段名、顶层状态和嵌套规则在全部示例中一致。

### H1：明确更新，使用本次新认识筛选

前置：没有等待中的 Feed。已保存关注“AI 辅助视频制作”，认识 A 为“一个 AI 助手适合贯穿所有单人短视频的脚本到剪辑”，认识 B 为“AI 可以生成画面和配音，镜头衔接和节奏需要剪辑处理”，均为确定信息。

```json
{
  "tool": "request",
  "input": {
    "currentText": "纠正一下：一个 AI 助手贯穿全流程只适用于简单口播，复杂叙事不能直接沿用；关于画面、配音和剪辑的认识不变。给我一次个人 Feed。"
  },
  "output": {
    "status": "one_link",
    "url": "https://x.com/example/status/101"
  }
}
```

中间交接：`additions` 为空；`replacements` 的 `target` 是读到的 A，`replacement` 是明确缩小适用范围后的确定认识。B 不在变更列表中，关注也不变。个人信息维护交出更新后的有效事实及 `sufficient: true`；受控候选 101 的内容提供此前未知的复杂叙事制作依据，判断使用新事实后合格。

状态结果：A 的旧泛化消失，缩小后的认识、B 和关注保存；新事实用于这一次判断。只有一次本轮观察，不额外调用 `observe_context`；没有待答问题或等待 Feed。历史已给出的结果不被重算。

反例：把新认识追加而仍保留原泛化、删除 B、对已经明确的范围再追问，或本次仍用旧认识判断，均不满足 H1。

### H2：需要澄清，连续回答只处理未解决部分

前置：关注为“AI 视频制作”，唯一相关认识 A 为“一个 AI 助手适合贯穿所有单人短视频的流程”。本次 Feed 指向复杂叙事，排除受质疑部分后没有足够的相关确定认识。

```json
[
  {
    "tool": "request",
    "input": {
      "currentText": "我开始怀疑一个 AI 助手贯穿所有单人短视频流程的判断了。给我一次关于复杂叙事视频制作的个人 Feed。"
    },
    "output": {
      "status": "incomplete",
      "stage": "personal_context",
      "question": "你怀疑的是这个结论本身，还是它在某类视频中的适用范围？",
      "continuationToken": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA"
    }
  },
  {
    "tool": "observe_context",
    "input": {
      "currentText": "这一点我还没想清楚。",
      "continuationToken": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA"
    },
    "output": {
      "status": "ignored",
      "question": "关于一个助手贯穿流程，你仍确认哪些适用范围，哪些还不能确认？",
      "continuationToken": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA"
    }
  },
  {
    "tool": "observe_context",
    "input": {
      "currentText": "简单口播可以，我仍然确认；复杂叙事那部分我还没想清楚。",
      "continuationToken": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA"
    },
    "output": {
      "status": "applied",
      "appliedCount": 1,
      "question": "对于复杂叙事视频，你现在明确知道哪些处理要求，原来的适用判断还要保留吗？",
      "continuationToken": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA"
    }
  },
  {
    "tool": "observe_context",
    "input": {
      "currentText": "复杂叙事也适用一个助手贯穿流程的判断撤回。我已经知道复杂叙事需要逐段检查跨镜头的人物和场景一致性。",
      "continuationToken": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA"
    },
    "output": {
      "status": "applied",
      "appliedCount": 1,
      "feed": { "status": "business_empty" }
    }
  }
]
```

状态逐步变化：第一次把受质疑的 A 隔离为 `uncertain`，保留原 Feed 的复杂叙事意图；含糊回答不制造事实；部分回答将 A 替换为“简单口播适用”的确定认识和“复杂叙事适用仍不确定”的认识；最后将复杂叙事的待澄清部分替换为用户明确给出的新认识。简单口播部分不再追问，也不被最后一次回答撤回。

前面三步均未开始 X 观察。最后信息足够才续做一次原请求；本例受控来源正常完成且没有候选，因此 `feed` 是业务空，不是假定所有来源都会空。疑问解决，问题/token 不再返回，原 Feed 等待关系结束。

反例：含糊回答后凑推荐、把仅适用于口播的知识当成复杂叙事已足够、最后只返回“已记住”、重问口播或丢失原来的复杂叙事范围，都不满足 H2。

### H3：普通交流说明是新手，自动继续原 Feed

前置：已明确保存关注“家庭照护”，没有相关知识边界；没有其他待答问题。用户先请求 Feed，后来只是补充自己的情况，没有声明在回答，也没有再次请求 Feed。

```json
[
  {
    "tool": "request",
    "input": { "currentText": "给我一次个人 Feed。" },
    "output": {
      "status": "incomplete",
      "stage": "personal_context",
      "question": "你目前了解家庭照护的哪些内容，还是刚开始接触？",
      "continuationToken": "CCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCA"
    }
  },
  {
    "tool": "observe_context",
    "input": {
```

中间交接：新增 `existing_knowledge/asserted` 的明确新手陈述；关注不变，问题得到回答，`sufficient: true`。调用方自动携带 token，服务使用更新后的事实继续原请求。受控候选 103 为对该新手有长期价值、匹配关注并提供新信息的内容；这不是“只要基础内容就自动合格”。

状态结果：明确新手信息保存，原 Feed 只续做一次；结果无剩余问题，调用方结束该关联。用户再次普通补充信息不会因为 H3 的旧请求再收到一轮 Feed。

反例：要求先列举几条不存在的已有知识、只更新不续做、让用户重发 Feed，或把原 Feed 意图留着导致之后再次续做，都不满足 H3。

### H4：相同补充，没有原 Feed 就只更新

前置与 H3 的个人信息完全相同，但用户此前没有请求 Feed，也没有等待中的问答。

```json
{
  "tool": "observe_context",
  "input": {
    "currentText": "补充一下，家庭照护我刚开始了解，目前没有相关基础。"

```

中间交接和保存的新手事实与 H3 一致；区别仅是没有原 Feed 关联。因此不调用内容获取或候选判断，不返回 `feed`，也不要求补充已经说清的知识。

反例：根据“已经足够”主动调用一次 `request`，即使最终返回业务空，也违反 H4。H3/H4 必须用相同补充话语成对核对，不能通过更换输入掩盖触发条件。

## 6. 其他必要组合与测试规格

### 6.1 剩余问题与结果同时返回

前置：原 Feed 曾因认识不足而等待；用户普通交流新增了足以筛选的确定认识，但没有回答另一条旧认识的疑问。维护保留旧疑问，使用新确定信息继续，示例输出为：

```json
{
  "status": "applied",
  "appliedCount": 1,
  "question": "你对之前那个适用范围的疑问，哪些部分仍待确认？",
  "continuationToken": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA",
  "feed": {
    "status": "one_link",
    "url": "https://x.com/example/status/106"
  }
}
```

调用方同时呈现待答问题和推荐结果；关联此后只剩问题，没有待续 Feed。若这一情况发生在初始 `request`，则使用其自身 `one_link/url`，同级携带问题/token，不嵌套 `feed`。后续回答旧问题不得再次恢复已结束的 Feed。

### 6.2 负面反馈只影响明确表达的部分

前置：有明确引用的受控 Feed 内容，保存的相关关注和认识有效；没有等待中的 Feed。先将“不喜欢”及明确引用交给 `process_feedback`，得到 `needs_input`、原因问题及 token；此时个人信息不变。

随后同工具收到原话“只是不喜欢这种表达方式；我仍然关注这个主题，这也不代表我已经知道文中的观点”及 token，返回 `completed`，没有 `feed` 或剩余问题。反馈按已明确的目标与原因处理；不能新增“不关注整个主题”或“文中观点已经知道”的事实，也不因记录完反馈主动推荐。
