# Personal Feed

只通过已加载的 `mcp__personal_feed__*` 工具使用独立服务，不自行读写状态、调用 HTTP、操作浏览器或模拟结果。

用户明确请求 Feed 时调用 `request` 一次，`currentText` 使用当前用户消息原文；普通发现不要求画像、不处理个人事实更新。只有用户同时明确表达了需保存的长期兴趣或已有认识时，先单独 `observe_context` 并如实说明更新结果，再执行已请求的发现；普通请求模板不要交入更新。直接表达长期兴趣或已有认识但未请求发现时，只使用 `observe_context`。反馈使用 `process_feedback`；仅当前消息或显式引用有目标定位文字时传 `referenceText`，不从隐含历史猜测。

发现不触发画像问答。独立更新／反馈的必要问答由当前工具调用的 MCP 表单完成。用户答案通过表单回到原调用；不要另外调用工具提交答案、重发原请求、拼接历史或维护续答 token。交互模式由客户端固定配置，模型不选择模式。普通更新和反馈不主动请求 Feed。

只呈现实际结果：`one_link` 给出这一条；若有 `limitations`，一并说明部分来源未读完、部分正文不足或部分判断未完成，不能丢掉这些限制；`business_empty` 说明本轮没有合适内容，`incomplete` 说明实际未完成阶段。来源原因分别解释为获取失败、部分观察或正文不足；没有原因则不猜测。V0 若明确后续探索尚未就绪，照实说明，不能称已完成探索或正常没有推荐。交互不可用、被拒绝、取消或超时按实际结果说明，不声称已完成；拒绝可能来自客户端权限策略，不归因于用户。不要自行编造追问或跨调用等待状态。`needs_input` 保留为业务类别，不建立旧式续答流程。

`applied`、`ignored`、`already_observed` 及反馈的 `pass`、`completed`、`discarded` 按原意呈现；没有成功结果不声称已记录。MCP 错误不解释成空结果。

收藏与取消收藏只调用 `record_feedback`，操作为 `save` 或 `unsave`，不代替喜欢与不喜欢。仅当前消息或显式引用能唯一定位 URL 时调用；否则先问一个简短问题。查看收藏使用 `list_saved`，没有指定数量时省略 `limit`。

工具不存在或不可用时如实说明；不用搜索、脚本、本地文件或自己的推荐伪造 Personal Feed。
